# SVG 作图规范

用手写 SVG 画信息密度较高的技术示意图。**不依赖任何绘图工具或第三方库**，
纯文本可 diff、可 review、可被后续 AI 精确修改，这是选 SVG 而不是截图或 draw.io 的根本原因。

**核心原则：先定画布，再算坐标，最后写代码；改完必渲染，渲染必目视。**

## 标准工作流程

### 第一步：确认信息源与口径

动笔前必须明确：

- **数据来自哪里**（哪张表、哪篇文档、哪次核对结果、哪次对话），图上要写明来源与截止日期
- **哪些信息已确认、哪些待确认**——待确认的要么标注清楚，要么先问用户，不要凭感觉画
- **本图的边界**（例如"仅含服务端，客户端另出一张"），避免范围蔓延
- **给谁看 / 放在哪**（技术文档正文 / 单独发 / 打印），这一条直接决定画布尺寸

不确定的信息**问用户，不要编造**。图会被当成权威资料引用，编造的连线、数据、依赖关系危害极大。

### 第二步：定画布与图型

**画布先定，这是最容易错、后果最重的一步。** 画布有两个模式，选错模式的代价是图白画。

| 模式 | 画布宽 | 读者行为 | 最小字号 | 用在 |
|---|---|---|---|---|
| **A · 内嵌即读** | **1200**（宽图 1400） | 直接看正文，不点开 | **11** | 操作手册、变更单、SOP、决策流程 |
| **B · 全景查阅** | **1960** | **会点开看大图** | **10** | 系统全貌、对象总览、跨域关系梳理 |

**怎么选：问"读者会不会点开看大图"。** 要按图操作（"点击第 3 步""按此配置"）→ 模式 A；
要拿它盘点全部对象、查某个节点在哪 → 模式 B。不要默认 1960，也不要默认 1200。

模式 B 的额外要求：主信息（系统名、IP、步骤标题）字号 ≥13，只让注释降到 10。
全图都靠 10 号字撑，点开也累。

换算关系：`实际显示字号 = 设计字号 × (显示宽度 / 画布宽度)`。
Outline 正文区约 768px，Markdown 正文区 800–900px。1960 画布缩到 800 只有 0.41，
11 号字实际显示 4.5px——**这就是为什么模式 B 必须假设读者会点开**。
详见 `references/001-视觉规范.md` 第一节。

图型按"要回答什么问题"选，不要先想"画个架构图"：

| 要回答的问题 | 图型 | 骨架 | 模式 |
|---|---|---|---|
| 一堆资源分布在哪、每个是什么 | **分区全景图** | `references/006-双栏骨架.svg` | B |
| 系统由哪些层组成、层间怎么调用 | 分层架构图 | `references/003-骨架模板.svg` | A |
| 哪些节点/区域连通，怎么通 | 网络拓扑图 | `references/006-双栏骨架.svg` | A/B |
| 一件事按什么顺序做、在哪判断 | 流程图 · 决策流 | 无骨架，见 005 第五节 | A |
| 一件事分几步、每步怎么验、错了怎么退 | 流程图 · SOP 步骤流 | 无骨架，见 005 第五节 | B |
| 多个角色之间消息怎么来回 | 时序交互图 | 无骨架，见 005 第六节 | A |
| 一个体系包含什么、怎么分类 | 层次结构图 | 无骨架，见 005 第七节 | A |
| 几个方案在若干维度上谁强谁弱 | 对比矩阵 | 先考虑用 Markdown 表格 | A |
| 一个对象在哪些状态间流转 | 状态机 | 无骨架，见 005 第九节 | A |

各图型的布局策略、坐标参数、数量上限与配色映射见 `references/005-图型与布局选型.md`。
**决策流和 SOP 步骤流不要混**——前者回答"走哪条路"，后者回答"按顺序做哪几步"。

### 第三步：分层列清实体与关系

把要画的东西按层次列出来，先文字后图形。**不同图型分层方式不同**：

```
分区全景          分区 A / B → 每个分区内的区块 → 每区块的卡片（三行）
分层架构          外部 → 接入层 → 业务层 → 数据层 → 基础设施
网络拓扑          外部 → 边界 → 入口映射 → 内部资源 → 管理面
决策流            触发 → 主步骤序列（含判断分支）→ 收尾
SOP 步骤流        前置判定 → 有序步骤（每步含通过条件与失败路径）→ 结论与回滚
时序交互          参与者清单 → 按时间排列的消息序列
层次结构          根 → 一级分类 → 二级分类 → 叶子
```

关系也要列出来：谁调用谁、哪条是双向、哪条待确认。

**同时确认数量没超限**：全景图 ≤2 分区、每区 ≤5 区块、每区块 ≤3 卡一排；
分层架构 ≤5 层、每层 ≤5 组件；决策流 ≤12 节点；SOP ≤6 步。
超了先拆图，不要靠压缩字号硬塞。

分层清楚了，坐标自然就有了。**没分层就直接画，一定会返工。**

### 第四步：规划坐标网格（关键，不可跳过）

在写第一行 SVG 之前，把画布尺寸、每个区块的 x/y/宽/高、卡片的排列间距**算出来写下来**。
详见 `references/002-布局与坐标.md`，核心三条：

1. **等距排列**：`x_i = x0 + i × pitch`，其中 `pitch = 卡片宽 + 间隙`，同排卡片宽度必须一致
2. **左右内边距必须相等**——只验"不溢出"不够，两侧不等会一眼看出歪
3. **容器高度 = 最后一个子元素底边 − 容器顶边 + 底部内边距**，容差 ±8px

### 第五步：按顺序写 SVG

通用骨架顺序（保证 z-order 正确，后画的盖前面的）：

```
<svg viewBox> → 白底 rect → <defs> 箭头 marker → 标题+数据来源
  → 容器（分区 / 分组底板）→ 容器内卡片 → 连线 → 结论块 → 图例
```

**先画容器再画卡片**，否则卡片会被后画的底板盖住。连线在卡片之后画没问题
（线走在卡片外的空隙里），但若线要从卡片*下方*穿过，必须画在卡片之前。

不同图型的差异部分：

- 分区全景：标题 → 外部实体 → 左分区（外框 + 标题 + 区块 + 卡片）→ 右分区（x 偏移）→ 分区间连线 → 警示块 → 图例
- 分层架构：外部实体 → 逐层（底板 + 标题 + 卡片）→ 层间箭头 → 结论块
- 网络拓扑：外部实体 → 左分区全部内容 → 右分区全部内容（x 偏移）→ 跨区连线
- 决策流：节点按主线顺序排 → 分支 → 回边（最后画，让它压在最上层）
- SOP 步骤流：前置判定区 → 步骤卡片（含通过条件条）→ 卡片间箭头 → 失败路径标注 → 结论块 → 图例
- 时序图：角色列 → 生命线 → 激活期矩形 → 消息线（消息必须最后画，否则被矩形盖）

配色、字号、marker 定义直接抄 `references/001-视觉规范.md`。
**色值是固定的语义表，不够用时复用最接近的一条，不要新增色值。**

**写任何文字之前先想一遍转义**：文本里的 `&` `<` `>` 必须写成 `&amp;` `&lt;` `&gt;`，
否则整个文件解析失败、浏览器白屏——这是唯一会让图"完全消失"的错误。规则见 001 第九节。

标识符清单、命令、版本号用等宽字体 `ui-monospace,Menlo,Consolas,monospace`，
字号比同层常规文字小 0.5–1。规则见 001 第五节。

### 第六步：校验 + 渲染 + 目视检查

**这一步不能省，也不能只做前半段。**

```bash
# 1. 结构层粗筛（一个命令查 12 项：XML 合法性、转义、字体栈、色值登记、
#    越界、卡片溢出、字号档位、marker、图例对应、左右内边距对称…）
python scripts/check_svg.py images/xxx.svg

# 2. 渲染成 PNG（各平台方案见 references/004-校验清单.md）
# 3. 打开渲染结果目视检查
# 4. 按目标显示宽度再渲一张，确认最小字号仍可读
# 5. 检查完清理临时文件
```

脚本只查**机器能查的**——它保证不了图有没有表达对意思。**脚本通过不等于可以交付**：
XML 解析通过但语义错、层级乱、重点不突出，都只能靠渲染目视发现。

脚本路径相对于本 skill 目录；不确定在哪就用绝对路径。
没有 python 环境时退回手工检查，清单在 `references/004-校验清单.md`。

**必须做缩放验证**：图会嵌进文档，按实际显示宽度渲一次，字太小就回去改画布，
不要靠放大字号硬撑（会溢出卡片）。

渲染不出来时**不要跳过这一步交付**，去 004 找本平台的可用方案。

### 第七步：落盘与引用

- 默认存到**目标文档同级的** `images/` 目录；用户指定了位置就按指定的来
- 命名 `YYYYMMDD-HHMMSS-mmm.svg`（时间戳到毫秒），避免同名覆盖
- 文档中用相对路径引用：`![系统架构](../../images/20260803-184500-000.svg)`
- 引用前确认相对路径真实可达（`test -f`）
- 单独交付、不嵌入文档时，文件名用**内容语义**命名（`order-flow.svg`），不用时间戳

## 修改已有 SVG 的专项规则

改图比新建图更容易出错，这几条是实际踩出来的：

### 改动量大就整文件重写

超过 5 处修改，或涉及布局位移，**直接用整文件重写**，不要连续几十次局部替换。
局部替换次数多了容易漏改、容易互相冲突，也容易在会话中断后丢失改动。
重写前先完整读一遍当前文件，以文件实际内容为准，**不要凭记忆重写**。

### 一处语义要同步改所有位置

同一条信息在图上通常出现在 4~5 个地方，改一处必须全改：

| 位置 | 例子 |
|------|------|
| 卡片内文字 | `★ 调度中心 · 双活` |
| 分组内注释行 | `★ 全系统唯一串行点，串联分区 A ↔ 分区 B` |
| 底部结论块 | `★ 全链路单点：调度中心` |
| 图例条目 | `枢纽 / 关键节点` |
| 分区副标题 | `用户侧 3 个入口 · 管理侧 2 个入口` |
| XML 注释 | `<!-- 辅助模块 -->` |

改完**必须全局 grep 查残留旧表述**：

```bash
grep -n "旧表述1\|旧表述2\|待确认\|待补录" images/xxx.svg || echo "无残留"
```

### 信息确认了就不许再标"待确认"

用户一旦说明了某项用途/关系，图上所有"待确认""待补录""用途未记""信息未知"
的相关标注都要立刻删掉，包括 XML 注释里的。**留着就是错误信息。**

### 删元素要处理留下的空洞

删掉一个卡片或整个区块后：

- 同排剩余卡片要重新计算 `pitch` 均匀铺开，或相邻区块拉宽占位
- 父容器高度、后续同级元素的 y 坐标要相应收缩
- 画布 `viewBox` 高度和白底 rect 高度一起改
- 图例里对应的颜色条目如果不再出现在图上，也要删

### 改高度要连带算父容器和后续元素

某个子元素高度 `+Δ`：父容器高 `+Δ`，其下方所有同级元素 y `+Δ`，
必要时画布高度 `+Δ`。漏了就会出现内容溢出容器边框。

## 硬性禁止

- ❌ `<style>` 标签、外部 CSS、`@font-face` / 网络字体——渲染环境不一定支持
- ❌ `<foreignObject>`、嵌入 HTML——多数 Markdown 渲染器不支持
- ❌ 绝对路径引用、外链图片资源
- ❌ **文字里的 `&` `<` `>` 不转义**——整图解析失败、白屏，图等于没画
- ❌ 编造未经确认的标识、数据、连线关系
- ❌ 只校验 XML 结构就交付，不渲染目视
- ❌ 临时新增配色——语义表之外的颜色一律不引入
- ❌ **拿配色表的 `stroke` 色当文字色**——橙底只有 2.56:1，看不清
- ❌ 漏写 `markerUnits="userSpaceOnUse"`，或线宽 ≥2 仍用 7×7 小箭头
- ❌ 字号低于下限（模式 A 为 11，模式 B 为 10）、线条细于 1
- ❌ 不确认"读者会不会点开"就上 1960 画布——嵌在正文里缩到 4.5px，等于没写
- ❌ 数据图表（柱状/折线/饼）用 SVG 硬画，应用图表库
- ❌ 靠压缩字号塞下超额内容——该拆图

## 配套 skill

图要嵌进网页时，页面级的配色、字阶、间距与圆角规范见同仓的 `ui-visual-language`——
两篇的配色语义与字号层级同源，SVG 里的颜色可以直接取那边的 token。
