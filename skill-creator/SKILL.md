# Skill Creator

本 Skill 提供创建高效 Skill 的指南，适用于将 SRE / 运维团队的知识库经验，沉淀为可被 AI 助手复用的标准化操作指引。

## About Skills

Skill 是模块化、自包含的知识包，通过提供专门的知识、工作流和操作规范，扩展 AI 助手处理特定任务的能力。可以将它们视为特定领域或任务的"操作手册"——它们让 AI 助手从通用问答工具，转变为具备团队程序性知识的专用助手，而这些知识（内部系统怎么操作、文档怎么归档、变更怎么留痕）是任何通用模型都无法凭空掌握的。

本仓库的 Skill 统一存放在 `_skills/` 目录下，会随仓库一起提交、被不同的 AI 助手读取和使用，因此编写时应保持表述通用、不依赖任何特定产品的私有能力。

### Skill 能提供什么

1. **专门工作流** - 针对特定运维场景的多步骤操作流程（如变更留痕、故障排查）
2. **工具集成指引** - 操作特定内部系统、平台、脚本的说明
3. **领域专业知识** - 团队专属的基础设施信息、命名规范、业务背景
4. **打包资源** - 用于复杂或重复任务的参考文档、脚本、模板资产

### Skill 的结构

每个 Skill 都由必需的 `SKILL.md` 文件和可选的打包资源组成：

```
skill-name/
├── SKILL.md（必需）
│   ├── YAML 前置元数据（必需）
│   │   ├── name:（必需）
│   │   └── description:（必需）
│   └── Markdown 指令（必需）
└── 打包资源（可选）
    ├── scripts/          - 可执行脚本（Shell/Python 等，用于确定性操作）
    ├── references/       - 按需加载到上下文中的参考文档
    └── assets/           - 用于输出的文件（模板、示例文档等）
```

#### SKILL.md（必需）

**元数据质量：** YAML 前置元数据中的 `name` 和 `description` 决定了 AI 助手何时使用该 Skill。需具体说明 Skill 的作用及使用时机，使用第三人称描述（例如 "当用户需要...应使用此 Skill" 而非 "当你想要..."）。

#### 打包资源（可选）

##### 脚本（`scripts/`）

用于需要确定性可靠性、或反复重写的操作（如调用内部 API、批量处理文件）。已有的 Skill 多采用 Shell 脚本（如 `scripts/list_users.sh`），根据实际场景选择合适的脚本语言即可，不强制要求某一种。

- **何时包含**：当同一段操作被反复执行，或需要确定性可靠性时（如"生成一份标准格式的变更记录骨架"）
- **优势**：节省 token、执行结果确定，AI 助手可直接调用而不必每次重新生成逻辑
- **注意**：AI 助手仍可能需要读取脚本内容以理解其行为、或按环境做少量调整

##### 参考文档（`references/`）

按需加载到上下文中的文档和参考材料，用于指导 AI 助手的操作和判断。

- **何时包含**：AI 助手在执行任务时应参考的详细资料
- **示例**：数据库操作手册的 `references/mysql-ops.md`、故障排查决策树的 `references/troubleshooting-guide.md`、内部平台 API 说明的 `references/api-endpoints.md`
- **使用场景**：系统操作步骤、内部平台接口文档、历史故障案例、命名与归档规范
- **优势**：保持 SKILL.md 简洁，仅在 AI 助手判断需要时才加载，不占用主上下文
- **最佳实践**：内容较多（超过约 1 万字）时，在 SKILL.md 中说明关键字/关键词，便于 AI 助手用检索方式定位所需片段
- **避免重复**：同一信息只在 SKILL.md 或参考文件中出现一次。除非确实是 Skill 的核心流程，否则优先放在参考文件中——SKILL.md 只保留触发条件和主流程，细节和示例放到 references/

##### 资产（`assets/`）

不打算加载到上下文中、而是用于生成最终输出的文件。

- **何时包含**：Skill 需要产出符合固定格式的文档或文件时
- **示例**：变更留痕文档模板 `assets/change-record-template.md`、故障复盘报告模板 `assets/postmortem-template.md`
- **使用场景**：文档模板、表格样式、需要被复制后填写的样本文件
- **优势**：将输出模板与操作说明分离，AI 助手可直接复制模板文件使用，无需在对话中重新生成格式

### 渐进式加载原则

Skill 采用分级加载，避免一次性占满上下文：

1. **元数据（name + description）** - 始终常驻，用于判断该 Skill 是否应被触发（约 100 字）
2. **SKILL.md 正文** - Skill 被触发后加载（建议控制在几千字以内）
3. **打包资源** - 按需加载，无严格数量限制（脚本类资源甚至可以不加载到上下文、直接执行）

## Skill 创建流程

创建 Skill 时，按以下步骤顺序进行，仅在有明确理由认为某步骤不适用时才跳过。

### 步骤 1：通过具体场景理解 Skill 的边界

仅当 Skill 的使用场景已经很清楚时才跳过此步骤。

要创建有效的 Skill，需要先弄清楚它将被用在哪些具体场景中。这种理解可来自用户直接提供的案例，或通过反馈确认过的设想场景。

例如，在规划"数据库操作手册"类 Skill 时，可以确认这些问题：

- 这个 Skill 要覆盖哪些数据库类型？MySQL、Redis、StarRocks 还是全部？
- 能否举一个具体案例，说明会被问到什么样的问题？（例如"帮我查一下这张表在哪个库""生产环境改字段长度要走什么流程"）
- 用户说什么样的话应该触发这个 Skill？

单次沟通中避免连续提太多问题，先问最关键的，视回答再追问。

对 Skill 需要覆盖的范围有清晰认知后，结束此步骤。

### 步骤 2：规划 Skill 需要沉淀的内容

把具体场景转化为可复用的内容，按以下方式分析每个场景：

1. 设想从零处理这个场景要经过哪些步骤
2. 识别其中哪些是重复出现、值得沉淀为参考文档或模板的部分

示例：构建"变更留痕文档 Skill"，用于处理"帮我按规范记录这次线上变更"这类需求，分析表明：

1. 每次变更留痕都要填一遍相同的骨架字段（变更时间、负责人、变更内容、回滚方案、验证结果）
2. 在 Skill 中存放一份 `assets/change-record-template.md` 模板会有帮助，同时用 `references/naming-and-filing.md` 说明文件命名和归档位置规则

示例：构建"故障排查 Skill"，用于处理"XX服务突然访问不了，帮我排查"这类需求，分析表明：

1. 每次排查都需要重新确认基础信息（网络分区、常见故障模式、历史类似案例）
2. 在 Skill 中存放一份 `references/troubleshooting-checklist.md` 记录排查思路和历史案例索引会有帮助

示例：构建"MySQL 操作手册 Skill"，用于处理"帮我看一下这张表的权限"或"这个字段要怎么改比较安全"这类需求，分析表明：

1. 每次操作都需要重新确认库表结构、连接方式、审批流程
2. 在 Skill 中存放一份 `references/mysql-ops.md` 记录连接信息位置、变更审批流程、常见操作 SQL 会有帮助

针对每个具体场景，列出需要沉淀的参考文档、模板和脚本清单，作为下一步的输入。

### 步骤 3：创建 Skill 目录

**存放位置（强制）：** 新建 Skill 必须创建在当前仓库根目录下的 `_skills/` 目录中，路径为：

```
<仓库根目录>/_skills/<skill-name>/
```

即使 AI 助手自身工具默认会把新建的 Skill 放到某个全局用户目录（例如某些工具默认使用 `~/.xxx/skills/` 这类主目录路径），也不要采用该默认位置——创建 Skill 时，第一优先级永远是当前仓库内的 `_skills/` 目录。判断"当前仓库根目录"的方法：从当前工作目录向上查找，直到找到包含 `_skills/`、`_rules/`、`AGENTS.md` 等标志性文件/目录的层级，即为仓库根目录；如果 `_skills/` 目录尚不存在，直接在仓库根目录下创建它，不要退回到全局目录。

不区分"个人 Skill"和"项目 Skill"——所有进入 `_skills/` 目录的 Skill 默认是整个仓库共享的，会随仓库一起提交、被不同 AI 助手读取。若确实需要在仓库之外（如某工具的全局目录）也保留一份供该工具识别，可以在完成仓库内创建后再额外复制一份，但仓库内 `_skills/` 下的这一份是唯一权威版本，其余都是派生副本。

`<skill-name>` 命名要求：

- 使用连字符分隔的小写形式（如 `db-ops-guide`、`change-record`）
- 仅允许小写字母、数字和连字符，不以连字符开头或结尾，不出现连续连字符
- 名称需与目录名完全一致，能直观反映 Skill 的用途

创建方式：直接手动创建目录和文件即可，不依赖任何脚本：

```
mkdir -p _skills/<skill-name>
```

然后在其中新建 `SKILL.md`，并按步骤 2 规划的内容，按需创建 `scripts/`、`references/`、`assets/` 子目录。不需要的目录不要创建，避免出现空目录。

### 步骤 4：编写 SKILL.md

编写时注意，Skill 是给 AI 助手看的操作说明，重点写清楚"对 AI 助手有用但它自己不知道"的信息，例如团队的内部约定、系统位置、审批流程，而不是重复讲已经是常识的通用知识。

**写作风格：** 使用祈使句（动词开头的指令）撰写正文，而不是"你应该……"这种第二人称建议句。例如用"变更前先确认回滚方案"而不是"你需要在变更前确认回滚方案"。这样表述更简洁，也更适合 AI 助手直接执行。

完成 SKILL.md 前，确认能回答以下问题：

1. 这个 Skill 的目的是什么？用一两句话说清楚。
2. 什么情况下应该触发这个 Skill？（写进 description，具体到场景关键词）
3. AI 助手实际使用时该怎么做？需要引用步骤 2 中规划的所有参考文档、模板、脚本，让 AI 助手知道在什么环节该查阅哪个文件。

一份最小可用的 SKILL.md 参考结构：

```markdown
---
name: change-record
description: 记录团队内部变更留痕文档时使用此 Skill，覆盖线上/线下变更的标准记录格式与归档路径。
---

# 变更留痕 Skill

## 何时使用
当用户提到"记录这次变更""变更留痕""帮我写变更文档"等场景时使用。

## 操作步骤
1. 询问变更的基本信息：时间、负责人、变更内容、影响范围、回滚方案
2. 参考 `assets/change-record-template.md` 生成文档骨架
3. 按 `references/filing-rules.md` 中的规则确定文件命名和存放目录
4. 生成后请用户确认关键字段无误

## 参考资源
- `assets/change-record-template.md` - 变更记录文档模板
- `references/filing-rules.md` - 文件命名与归档目录规则
```

### 步骤 5：人工检查

Skill 编写完成后，用以下清单人工核对一遍，无需借助任何脚本：

- [ ] `SKILL.md` 存在，且以 `---` 开头的 YAML 前置元数据包含 `name` 和 `description` 两个必需字段
- [ ] `name` 为连字符小写形式，且与目录名完全一致
- [ ] `description` 具体描述了触发场景，不包含 `<` `>` 等特殊符号
- [ ] 正文使用祈使句风格，信息不与参考文档重复
- [ ] `scripts/`、`references/`、`assets/` 中没有遗留未清理的占位文件或示例文件
- [ ] 引用的文件路径（如 `references/xxx.md`）均真实存在
- [ ] 不包含内部凭据、密码、密钥等敏感信息（如需引用，应改为指向凭据管理系统的说明，而非明文）

检查通过后，Skill 即可提交到仓库的 `_skills/<skill-name>/` 目录，随正常的 Git 提交流程走评审即可，不需要额外打包或生成分发文件。

### 步骤 6：迭代

Skill 被使用一段时间后，通常会发现需要改进的地方。这时按以下方式迭代：

1. 在真实任务中使用该 Skill
2. 记录遇到的困难或低效之处（例如 AI 助手总是漏掉某个步骤、某个参考文档已过时）
3. 判断应该更新 SKILL.md 正文，还是更新某个参考文档/模板
4. 修改后再找一次真实场景验证效果

Skill 内容会过时（内部系统迁移、流程调整），建议在相关运维变更发生后，同步检查是否有 Skill 需要更新。
