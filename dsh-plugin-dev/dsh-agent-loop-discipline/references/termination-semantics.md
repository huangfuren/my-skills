# 终止语义：判定条件与优先级

这篇讲三件事：每个终态**在什么条件下成立**、多个条件同时命中时**报哪个**、收尾时**按什么顺序检查**。

## 一、四个终态的精确定义

### `COMPLETED`

成立条件必须包含**验证证据**，不能只是「循环正常退出」。

判定要问的问题不是「AI 说完成了吗」，而是「有没有一条独立于 AI 自述的证据，证明目标达成」。证据可以是一条复核命令的退出码、一次读回的内容比对、或外部系统的状态查询。

反例：AI 跑完 `systemctl restart nginx` 退出码 0，就报完成。退出码 0 只说明**命令被接受**，不说明**服务起来了**。

### `ROUND_LIMIT`

成立条件：步数预算耗尽，且**未达成目标**。

这个终态的存在本身就是一个设计声明：**「跑完了预算」和「做完了任务」是两件事**。

通常还会伴随一个「可续跑」状态——用户可以批准追加步数继续。续跑时预算基准要重置，否则续跑等于没跑。

### `USER_INTERRUPT`

成立条件：人主动停止。

要点是**停止必须彻底**：取消在途的模型请求，并且禁止已中止的轮次被后续事件「复活」。常见缺陷是停止后仍有迟到的回调把状态改回运行中。

### `ERROR`

成立条件：执行期出现无法继续的错误（模型请求失败、连接不可用、内部异常）。

区别于 `ROUND_LIMIT`：前者是**环境不允许继续**，后者是**预算不允许继续**。对用户的话术不同，一个要排查，一个只需追加预算。

## 二、优先级：同时命中时报哪个

检查顺序固定为：

```
1. 结果不明（未确认执行结果）
2. USER_INTERRUPT
3. ERROR
4. ROUND_LIMIT
5. COMPLETED
```

前三条是「异常优先于正常」，第四条是「耗尽优先于完成」。

### 为什么「结果不明」排第一

设想一个场景：最后一步是一条写操作，执行后连接断了，没拿到退出码；同时步数刚好用完。

| 上报 | 用户的反应 |
|---|---|
| 「轮次上限」 | 追加预算重跑 → 写操作可能被执行两遍 |
| 「结果不明」 | 去机器上核实 → 该写的写了就收手 |

代价不对称：**多核查一次的成本，远低于重复执行一次写操作。**

### 为什么「完成」排最后

`COMPLETED` 是唯一一个会让人**停止关注**的终态。一旦报了这个，用户就走了。

所以它必须是最后一个被检查的——前面任何一个异常命中，都不该走到这里。

## 三、收尾的单一入口

收尾逻辑集中成一个函数，正常与异常两条路径都调它：

```ts
function finishTurn(turn, outcome) {
  // 顺序即优先级，不要重排
  if (turn.uncertain) return report(turn, '结果不明，需人工核实')
  if (turn.interrupted) return report(turn, 'USER_INTERRUPT')
  if (outcome.error) return report(turn, 'ERROR', outcome.error)
  if (turn.budgetExhausted) return report(turn, 'ROUND_LIMIT', turn.stepCount)
  return report(turn, 'COMPLETED', evidence(turn))
}
```

三个注意点：

**1. `evidence()` 不能返回空**

如果走到 `COMPLETED` 却取不到证据，说明判定本身有问题。此时应当降级为 `ROUND_LIMIT` 或「结果不明」，而不是带着空证据报完成。

**2. 收尾函数里不要再抛异常**

收尾阶段抛错会让终端状态彻底丢失。这里的所有分支都要能走完。

**3. 一次性写状态**

收尾函数应当把终态、步数、证据**一次写完**，不要分多次更新。分次更新会留下「状态已改但证据还没写」的中间态，一旦进程在这时退出，重启后就无法判断上一轮到底算什么。

## 四、恢复：重启后怎么接着算

进程重启后，持久化的只有步骤记录，没有内存里的 `turn` 对象。恢复时要重建：

| 要重建的 | 来源 |
|---|---|
| 已有步骤数 | 持久化的步骤记录长度 |
| 预算基准 | 已有步骤数（不是 0） |
| 已完成的部分结论 | 最后一条成功步骤的输出摘要 |
| 权限状态 | 默认回到最保守（只读） |

最后一条尤其重要：**重启后权限必须回到只读**。把「用户上次开过写权限」跨重启继承，等于让一次授权永久有效。

## 五、常见错误对照

| 写法 | 问题 |
|---|---|
| `for (i = 0; i < max; i++) { ... }` 结束后 `return success` | 耗尽被当完成 |
| 收尾时先判断 `if (completed) return` | 异常被完成覆盖 |
| 停止时只置一个 `stopped` 标志 | 迟到的回调仍会改状态 |
| 恢复时预算从 0 重算 | 续跑等于重跑满额 |
| 恢复后沿用上次权限 | 一次授权变永久授权 |

## 六、最小验证方式

不需要真实模型就能验证大部分规则。构造四种情况各跑一遍：

1. 步数设 1，让它必然耗尽 → 断言终态是 `ROUND_LIMIT`，且**不是** `COMPLETED`
2. 最后一步注入「无退出码」→ 断言终态是「结果不明」，且**不是** `ROUND_LIMIT`
3. 执行中调 `stop()` → 断言终态是 `USER_INTERRUPT`，且 200ms 后状态不再变化
4. 正常两步骤任务 → 断言终态是 `COMPLETED`，且证据非空

第 2 和第 3 条最能暴露实现缺陷，建议优先写。
