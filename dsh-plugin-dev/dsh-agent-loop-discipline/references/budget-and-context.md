# 预算与上下文：三层限流与截断

循环失控有两种形态：**方向错**（一直试）和**信息过载**（一直读）。混成一个预算就分不清该收紧哪个。

## 一、三个维度分开设限

| 维度 | 限制的是什么 | 典型值 | 耗尽后的终态 |
|---|---|---|---|
| 步数 | 模型决策次数 | 默认 100 / 上限 1000 | `ROUND_LIMIT` |
| 读次数 | 只读工具调用次数 | 与步数独立 | 单独标记 |
| 输出长度 | 单步结果的落盘大小 | 按步截断 | 截断标记 |

### 步数

步数是**模型决策次数**，不是工具调用次数。一次决策可能包含多个工具调用，也可能一个都没有（纯文本回复）。

这一点在计数时必须写清楚，否则会出现「预算还有 50 步，但实际上已经调了 200 次工具」的情况。

步数上限应当**每轮读取配置**：

```ts
const DEFAULT_MAX_STEPS = 100
const HARD_MAX_STEPS = 1000

function readMaxSteps(store): number {
  const v = store.get('agentMaxSteps')
  return Number.isSafeInteger(v) && v >= 1 && v <= HARD_MAX_STEPS
    ? v
    : DEFAULT_MAX_STEPS
}
```

注意两件事：

- **硬上限单独存在**：用户可调，但不能调到无穷。硬上限存在的意义是防止一个手误把预算设成 100 万。
- **每轮读，不是启动读**：用户中途改小，下一轮立刻生效。

### 读次数

为什么读要单独计？

因为「读」和「写」的失控方式不同。读失控的代价是上下文膨胀、响应变慢、费用上升；写失控的代价是机器状态被改坏。两者用同一个计数，会导致**为了省预算而不敢读**，或者**读满了却还能继续写**。

读预算耗尽时的处理应当是**软停**：不报错，但明确告诉模型「读额度已用完，只能基于现有信息给结论」。这样它能收尾，而不是硬崩。

### 输出长度

单步输出必须在**落盘前**截断，不能先存再截。

```ts
function truncate(text: string, max: number): string {
  if (text.length <= max) return text
  return text.slice(0, max) + '…[已截断]'
}
```

三个要点：

- **标记必须可见**：`…[已截断]` 是给模型看的，让它在后续推理里知道信息不全。
- **保留区间信息**：读文件类工具应当返回行号区间，让模型能续读。
- **区分空结果和截断**：空文件、越界、超窗是三种不同情况，返回要区分，否则模型会把「读不到」当成「不存在」。

## 二、上下文的两种来源要分开

循环里的上下文至少有两个来源，混在一起会出错：

| 来源 | 内容 | 可信度 |
|---|---|---|
| 终端回显 | 屏幕上滚过的所有字符 | **低**——包含 AI 自己敲的命令、命令提示符、颜色控制符 |
| 已验证结果 | 每一步的真实退出码 + 清理后的输出 | **高** |

如果把终端回显直接喂给模型，会出现「AI 看到自己上一条命令的文字，误以为那是机器返回的信息」。

处理方式是：

1. 回显只用于人看，不进模型上下文；
2. 进上下文的是结构化步骤记录（命令 + 退出码 + 截断后的输出）；
3. 只把**已验证**（有明确退出码）的步骤当作事实，未验证的单独标注。

## 三、历史滚动的取舍

长会话一定要裁剪，否则上下文会无限增长。裁剪策略有三档：

| 策略 | 保留什么 | 代价 |
|---|---|---|
| 只留最近 N 步 | 最近的操作与结果 | 丢失早期目标 |
| 最近 N 步 + 原始目标 | 再加首条用户指令 | 几乎无额外代价 |
| 最近 N 步 + 目标 + 关键结论 | 再加每步的一句话结论 | 需要模型产出结论 |

**至少要用第二档。**

原因：裁剪掉原始目标之后，模型会忘记自己要干什么，开始对着最后一条命令的输出做局部优化。这是「AI 越跑越偏」的常见成因。

第三档的额外成本是要求每步产出结论，但收益是恢复时能快速重建上下文。如果循环支持跨重启恢复，这一档值得做。

## 四、恢复时的预算基准

从持久化状态恢复时，预算基准必须按已有步骤数起算：

```ts
const baseline = restored.steps.length       // 已有业务步骤
const remaining = maxSteps - baseline
if (remaining <= 0) return finishTurn(turn, 'ROUND_LIMIT')
```

用 0 起算的后果是：一个已经跑了 90 步的任务恢复后又能跑满 100 步，**总预算翻倍且无人知晓**。

同时要注意：恢复出来的步骤可能包含未验证的（比如上次崩溃时正在执行的那一步）。这类步骤应当标为「结果不明」，不能算作已完成，也不能算作失败——它需要一次核实。

## 五、成本维度（容易漏）

步数预算是**操作数**，不是**钱**。两者不等价：一次长输出的读操作可能比十次短命令更贵。

如果要控成本，需要单独记录：

- 每步的输入 token 数（上下文长度）
- 每步的输出 token 数
- 累计值，以及达到阈值时的提示

多数插件不做这层，但如果你的循环可能连续跑几百步，这一层迟早要做。做法上建议**只记录不阻断**：先积累数据，看清真实分布再定阈值。凭直觉设的 token 上限往往错得离谱。

## 六、检查表

- [ ] 步数按「决策次数」计，不是工具调用次数
- [ ] 硬上限独立于用户可调值
- [ ] 步数每轮读配置，不是启动读一次
- [ ] 读次数单独计，耗尽时软停而非硬错
- [ ] 输出在落盘前截断，带可见标记
- [ ] 空文件 / 越界 / 超窗三种情况返回可区分
- [ ] 终端回显不进模型上下文
- [ ] 裁剪保留原始目标
- [ ] 恢复时预算按已有步骤数起算
- [ ] 恢复出的未验证步骤标为「结果不明」
