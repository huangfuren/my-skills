# grill-me

把模糊需求盘问成一份清晰、可确认的需求与操作文档，用户点头之后才动手。

它不会一上来就写代码，也不会一次抛给你五个问题。它先看你已经给了什么，再问还缺什么；问清一块就复述一块；最后落成文档，停下等你确认。

## 它解决什么

模糊需求直接开工，返工成本由「改错之前那段时间」决定。这个 skill 把含糊处在动手前挖出来：要做什么、不做什么、什么算做完、出错怎么办、改哪些文件、怎么退回去。

## 四步

1. **判断规模** — 关键信息都在请求里就直接做；有真正的分叉才走完整流程。
2. **先看再问** — 读项目、读上下文，读到能说清「现在怎么工作、这次碰什么」为止。
3. **盘问** — 先开放问「为什么」，知道原因后才给带代价的选项；问清一块回放一块。
4. **落文档 → 等确认** — 出需求与操作文档，未获批准不动手。

## 它和普通追问的区别

| | 普通追问 | grill-me |
| --- | --- | --- |
| 是否总是走流程 | 一律追问 | 按规模分流，小改动直接做 |
| 提问节奏 | 一次抛 3–5 个问题 | 一次一个，答完再问 |
| 提问起点 | 直接问技术选型 | 第一问先问动机，再问做法 |
| 提问形式 | 正文列表等他打字 | 全程弹窗，标题带进度（如「结构 1/5」） |
| 提问判据 | 想到就问 | 只有答案会改变产出时才问 |
| 中间过程 | 只问不 recap | 边问边回放，区分「你说的」和「我推的」 |
| 提问范围 | 想到哪问到哪 | 六维议程，查到答案的跳过 |
| 终止 | 问到没得问 | 8–12 问预算，喊停即停 |
| 产出 | 散在对话里 | 需求与操作文档，需求带编号、验收可追溯 |
| 开工 | 边问边改 | 文档批准后才动第一行代码 |

## 文档结构

`assets/requirement-spec-template.md`，八节：

1. 目标 —— 一句话 + 为什么是现在
2. 范围 —— 做 / 不做 / 什么算失败
3. 需求与验收 —— `R1` 编号需求，`A1.1` 编号验收，写成「条件 → 行为 → 结果」
4. 关键决策 —— 结论、理由、放弃的备选
5. 执行步骤 —— 具体操作、覆盖哪条需求、完成判据、回滚
6. 风险与边界
7. 待定项
8. 确认

交付前自检三问：每条需求有验收吗？每个验收有步骤支撑吗？每个步骤能对应回需求吗？

默认落盘 `docs/requirements/<需求名>.md`，用户可改。

## 硬闸门

文档批准前不写产品代码、不建脚手架、不装依赖、不跑有副作用的命令、不改仓库文件。读代码和只读命令不受限。

「嗯」「看着还行」不算批准。批准只覆盖他看过的东西。

## 借鉴来源

| 来源 | 借了什么 |
| --- | --- |
| [obra/superpowers · brainstorming](https://github.com/obra/superpowers) | 规模分流、先开放问后给选项、边问边回放、只把用户说的记作用户说的、硬闸门与红旗表 |
| [GitHub Spec Kit](https://github.com/github/spec-kit) | 需求与验收编号、跨文档覆盖检查（需求 ↔ 任务）、把 spec 当可测试对象 |
| [Kiro · Requirements-First](https://kiro.dev/docs/specs/feature-specs/requirements-first/) | EARS 式「条件 → 行为 → 结果」验收写法、需求/设计/任务分档 |

## 安装

```
<skills-dir>/grill-me/
├── SKILL.md
├── README.md
└── assets/
    ├── requirement-spec-template.md
    └── design-decisions-template.md
```

dsh 用 `~/.dsh/skills/` 或仓库根的 `.dsh/skills/`；WorkBuddy 用 `~/.workbuddy/skills/`。放进去后新开会话生效。

**只在点名时触发**：说 "grill me"、"拷问我"、"用 grill-me"、"先出需求文档再开工"。它不会自己冒出来，日常改动别指望它介入——这是有意设计的，自动触发会在小需求上浪费你的时间。

## 依赖

- 宿主需提供 `AskUserQuestion` 类多选弹窗。没有则降级为文本提问，仍保持一次一问。
- 需要写文件权限才能落盘；无权限时退化为对话内汇总。
